Methodology
System Architecture Overview

At a high level, our chatbot system follows a modular Retrieval-Augmented Generation (RAG) architecture specialized for labor law (Figure 1). When a user sends a query through the chat interface (e.g., “Tinanggal po ako sa trabaho nang walang abiso – anong dapat kong gawin?” – “I was fired without notice – what should I do?”), the system processes it through several stages to produce a helpful answer[37]. Notably, the user interface supports both text and voice input to maximize accessibility. Users can either type their question or speak it aloud – in any supported language – using their device’s microphone. For voice queries, the interface utilizes the browser’s Web Speech API or a cloud Speech-to-Text (STT) engine (such as Google Cloud Speech-to-Text) to transcribe the spoken question into text in real time. This transcription is then passed into the same NLP pipeline described below. By allowing voice input, the chatbot becomes more inclusive for users who have difficulty typing or prefer to explain their situation orally. All voice data is processed client-side or via the STT API and is not stored, to protect user privacy.

Once the user’s query is captured (as text either originally typed or transcribed from voice), the system performs the following steps:

1.	Language & Intent Processing: The user’s message is first analyzed to determine the language (Filipino, English, Cebuano, or a mix) and to identify the general intent or legal issue. We use a lightweight language detector – specifically a FastText-based model – since Filipino and English are often code-mixed, and now including Cebuano requires reliable detection of that language as well. The system allows code-switching in queries (e.g., Taglish or mixed Cebuano-English), and if multiple languages are detected, all are recognized. We then apply a classifier to tag the query into a labor law category (e.g., termination, wages, benefits). In our improved design, a DistilBERT-based intent classification model (fine-tuned on labeled labor law queries) replaces the initial simple keyword-based classifier for greater accuracy. This intent classification is based on a taxonomy of labor law topics we defined (see Table 1) and helps the system narrow down relevant knowledge base sections[38][39]. For example, a query about being fired triggers the Termination category, whereas a question about “13th month pay” falls under Wages & Benefits. If the query is outside the labor domain (say the user asks about a criminal case), the bot will politely refuse or redirect, as our domain is intentionally limited for safety[32]. (We implement this domain safeguard as part of a broader guardrail subsystem – any queries that are off-topic or potentially problematic are intercepted with rule-based checks or OpenAI’s content moderation API, and the chatbot responds with a courteous refusal or warning as appropriate, in line with ethical use guidelines.) In addition, our multilingual pipeline handles inputs beyond English/Filipino: if a query is in Cebuano (or another unsupported language), we leverage the Google Translate API (v3) to automatically normalize the input into a supported language (translating it to English or Filipino for processing). This translation step preserves the user’s intent while allowing the downstream components to work with a language they understand. The system logs the original text and uses the translation only internally for retrieval and response generation. This approach ensures that multilingual queries are handled effectively without requiring a full Cebuano legal corpus. The user’s experience remains seamless – they can ask in Cebuano and still receive a helpful answer (with the answer later translated back to Cebuano if needed).

2.	Knowledge Retrieval: The core of our system is a Philippine Labor Law Knowledge Base, a curated corpus of legal texts and FAQs (detailed in the next section). The user’s query (in its original language, or in translated form if normalization was needed for Cebuano or deep Tagalog dialect terms) is used to perform a semantic search on this corpus. We utilize a vector database (Supabase) to find the most relevant passages[40]. Supabase stores pre-computed embeddings of all knowledge base documents and allows fast semantic similarity searches in a cloud-hosted environment. We chose Supabase over a purely in-memory engine (like FAISS) because Supabase provides persistent, cloud-hosted storage of vectors and can be accessed by multiple users concurrently, which is crucial for a deployed web service. In contrast, FAISS is well-suited for local or in-memory retrieval but would not easily support a scalable multi-user web application without additional infrastructure. Using Supabase ensures our chatbot’s memory of legal texts is not only fast but also persists across sessions and can be updated centrally. For instance, if the query involves dismissal without notice, the retrieval might fetch Article 297 of the Labor Code (on valid causes for termination) and a snippet from DOLE’s rules on termination procedure. The retriever returns the top-$k$ passages (we typically use $k=3$–5) that semantically match the query[40][41]. This ensures that even if the user phrased the issue colloquially (e.g. “tinanggal” instead of the legal term “terminate”), relevant legal provisions (written in English) can be found by semantic similarity. The retrieval module essentially acts as the memory of the chatbot, giving it access to up-to-date legal information whenever needed[42]. Notably, by translating Cebuano queries to English/Filipino in the previous step, we enable the retriever to work on those queries as well – the English translation of a Cebuano question about, say, holiday pay will match with the Labor Code provisions on holiday pay. The use of a robust vector search also helps bridge language gaps: even if we did not translate, the semantic embedding can sometimes link a Cebuano query to an English document if the embeddings space captures cross-lingual semantics, but our translation step greatly improves this consistency.

3.	LLM Response Generation: We feed the user’s question along with the retrieved legal passages into the GPT-4.1 model, which serves as the conversational engine. Rather than relying on the LLM’s built-in knowledge alone (which may be incomplete or outdated regarding Philippine laws), we employ a prompt that explicitly provides the model with the relevant excerpts and instructs it to base its answer on them[43]. For example, the prompt might be constructed as: “User asks: ‘I was fired without notice after 3 years of work.’ Relevant info: [Excerpt of Article 297 on just causes] [Excerpt of DOLE Dept. Order on due process]. Using only this information, answer the user in Filipino, explaining their rights and next steps.” GPT-4.1 then generates a conversational answer grounded in those snippets – it might say (in Filipino), “Ayon sa Artikulo 297 ng Labor Code, bawal tanggalin ang regular na empleyado nang walang just cause at due process…”, citing the law as it explains the violation[43][44]. The LLM’s role is to compose a human-friendly answer: it interprets the legal texts, fills in reasoning (e.g., noting that no notice was given, so due process was violated), and organizes the guidance into steps. We also include instructions in the prompt to maintain a polite, layman-accessible tone for complex concepts, and to insert citations to sources for any legal statements made[44]. The multi-turn capability of GPT-4.1 allows the chatbot to handle follow-up questions. For instance, the bot may proactively ask clarifications – “Ilan taon ka nang empleyado?” (“How many years have you been employed?”) – if that detail is needed to determine rights[45]. The conversation history is kept in the prompt to preserve context across turns. It’s worth noting that if the user’s input was in Filipino or Cebuano, we can instruct GPT-4.1 to respond in that same language for continuity. The prompt in the example above explicitly told the model to answer in Filipino because the query was in Filipino. Similarly, if a query comes in Cebuano, we would attempt to have the model answer in Cebuano. Since GPT-4.1 has limited training data in Cebuano, an alternative approach is to have it produce an English or Filipino answer based on the sources, then use the Google Translate API to back-translate that answer into Cebuano before delivering it. We experimented with direct Cebuano prompts and found that while the model can output some Cebuano (due to its multilingual pre-training), using translation for both input and output yields more grammatically correct and clear Cebuano responses. This two-step translation (Cebuano query → English for processing → English answer → Cebuano translation for user) inevitably adds a bit of latency, but ensures the answer is accessible in the user’s native language. We prioritize fidelity of information and clarity, doing this only for languages that the LLM cannot confidently produce on its own.

4.	Post-processing & Delivery: Before the answer is shown to the user, we perform minor post-processing. This includes ensuring that any legal references are properly formatted (e.g., converting “Art. 297” to “Article 297 of the Labor Code” for clarity), inserting relevant hyperlinks (the bot can provide links to forms or DOLE web pages when appropriate), and appending a disclaimer or referral note if needed. For example, if the answer involves advising the user to file a complaint, the chatbot will add a note like “Paalala: hindi ako abogado – nagbibigay lang ako ng impormasyon ayon sa batas” (“Reminder: I am not a lawyer – I only provide information according to the law”) for transparency about its role[46]. It may also suggest contacting the nearest DOLE office or a lawyer for further action if the issue is serious[46]. To facilitate such referrals, we integrated a location-based assistance feature using the Google Maps API. With the user’s consent to access location data (or if the user provides their town/city), the chatbot automatically finds the nearest Public Attorney’s Office (PAO) or reputable legal aid center, and even nearby private law firms that handle labor cases. The system does this by sending the location to the Google Maps Places API, which returns relevant legal service providers in the vicinity. The chatbot then presents the names, addresses, and contact information of a few nearest offices to the user. This integration effectively connects the digital advice to on-the-ground help, empowering users with an immediate next step if their issue requires escalation. We handle privacy by making location-sharing optional and by not storing any location data on our servers; the user’s location is used in the moment of the query solely to fetch nearby legal aid suggestions. This way, the benefit of convenient referral is offered without compromising user privacy or trust. Finally, the answer (augmented with citations, disclaimer, and location-based suggestions if applicable) is sent back via the chat interface for the user to read. The entire sequence is designed to be completed in a few seconds per query, enabling an interactive real-time dialogue[47].

System Architecture – The chatbot’s architecture consists of a user interface (supporting text and voice input), an NLP layer for language detection and intent classification, a labor law knowledge base, a retrieval module (Supabase vector semantic search), and the GPT-4.1 large language model for answer generation. When a user asks a question, the system retrieves relevant legal documents (Labor Code provisions, DOLE guidelines, etc.) and feeds them into the LLM, which produces a conversational answer with citations. The answer is then delivered to the user along with references or links as needed. A safety sub-module monitors the content (e.g., refusing queries outside scope or adding disclaimers) to enforce ethical guidelines[48]. The modular design allows updating the knowledge base or replacing components (for example, upgrading the LLM or incorporating a translation service) without affecting the overall pipeline[49].
